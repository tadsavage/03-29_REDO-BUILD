# Dock Door Numbering + Shipping-Lane System ("lane setup")

**Status: DONE 2026-07-03** (staging lanes feature-complete; next warehouse work is the truck-unloading / PO loop — see memory `core-loop-phase1-truck-unloading`). Confirmed in-game: entry-only labels, double-click config modal, adjacency ownership, drag-delete revert.

Linked always-on services that label the receiving dock and make it addressable:
1. **Door numbering** — every shipping door shows a stable number (1,2,3…).
2. **Lane naming** — every shipping-lane tile shows `<doorNumber><letter>` (e.g. `1A`, `2C`) — one name per lane, globally unique = one exact place in the warehouse.
3. **Slot addressing + config + occupancy** — each tile is a numbered slot (`1A-3`), lanes carry per-lane `LaneConfig`, and placed pallets get real addresses (see the slot/putaway section).

Built 2026-07-03. Both are **self-bootstrapping** (`[RuntimeInitializeOnLoadMethod(AfterSceneLoad)]` → a hidden `DontDestroyOnLoad` GameObject). **No scene wiring, no guard shack, no manager to configure.** Files all in `Assets/_Project/Scripts/Gameplay/`.

## Core data model
- **Door** = a `ShippingDoor` prefab (ObjData id **63**) carrying a `DockSlot` (registers in static `DockSlot.All`), a `PlacedObject`, and a `DoorNumberDisplay` (holds a `textComponents` TMP array it sets via `Number`). `DockSlot` caches the display in Awake and pushes `DoorNumber` into it.
- **Lane** = one row of **`Flr-ShipLane`** tiles (ObjData id **35**, "Ship Lane", 1×1, category Floor, `isFloor`) running OUT from the door in the depth direction; ~5-8 tiles long. Lanes sit side-by-side along the wall. The `Flr-ShipLane` prefab already has a child GameObject **`LaneNo`** with a `TMPro.TextMeshPro` label (prefab default text "1A") — that's the on-tile display AND how a lane tile is self-identified (never hard-code id 35: look for a `LaneNo` child).
- The free ground tile is **`flr-YardTile`** (id 200, cost 0) — NOT a lane; it's the base floor.

## Door numbering — `DockSlot.AssignDoorNumbers()` (static)
**Numbers are permanent once assigned and NEVER renumber existing doors.** This is load-bearing: trucks, lane names, and employee/inventory destinations all reference door numbers, so we only ever **add or remove**, never rename (a manual double-click rename UI can come later, like racks).

- Persisted in the door's **`PlacedObject.customData`** (doors use customData for nothing else; it is saved & restored — see `PlacementSystem.SpawnFromSave` sets `po.customData` AFTER `Instantiate`, so `OnEnable` can't read it → the service re-runs post-load via heartbeat/events).
- A door with a persisted number keeps it. Doors without one get the **lowest unused** number (gap-fill/recycling like aisle numbers): 1-4 exist → new door = **5**; delete door 2 → next door placed reuses **2**.
- Pre-persistence saves (empty customData) bootstrap ONCE by position (X-then-Z), matching the original order. To retrofit a specific save, stamp `customData` per door entry (id 63) directly in the save JSON.
- `DoorNumber` setter is `private`; only `SetNumber(n, persist)` writes it.
- Callers: `DockSlot.OnEnable/OnDisable`, `DockNumberingService` (events + 1s heartbeat), `TruckYardManager.AssignDoorNumbers()` (delegates). All idempotent.
- **Known edge:** undo of a door delete after its freed number was reused can collide. Rare in the add/remove flow; accepted.

## Lane naming — `LaneNamingService.Recompute()`
Recomputes on `OnObjectPlaced`/`OnObjectDeleted` + a 1s heartbeat (heartbeat catches save-loads, which bypass placement events).

Algorithm (**this order matters**):
1. Collect lane tiles = active `PlacedObject`s with a `LaneNo` child (`transform.Find("LaneNo")`).
2. **Assign each tile to its OWNER door, then group per door.** Ownership is **STICKY** (added 2026-07-03): each lane tile's owning door NUMBER is persisted in its own `PlacedObject.customData` (lane tiles use customData for nothing else — same field/pattern doors use for their number). A tile that already has an owner keeps that door and is **never re-stolen** by a door placed closer later — that is the whole point of the lock. Only **unowned** tiles (freshly placed, or **orphaned** because their owner door was deleted) get a fresh owner, which is then written back / locked. **Do NOT revert to "assign every tile to its nearest door every Recompute"** — that was the bleed-over bug (placing a new door near an existing dock's lanes relabeled them). Fresh-owner pick = `ChooseDoorForNewTile`: the door the tile sits most directly **in front of** (smallest lateral offset from the door's forward centerline, within `MaxLaneDepth`), falling back to plain nearest only if the tile is in front of no door. Grouping per door is still critical because docks can sit on opposite walls (e.g. one at grid x=67 facing −X, another at x=36 facing +X) and two pads can share a wall-coordinate — a global grouping would merge them.
   - **Owner resolution priority (2026-07-03):** (a) own persisted owner (sticky) → (b) **ADJACENCY**: a fresh tile orthogonally touching an already-owned lane tile inherits that tile's owner and joins its pad — propagated so a whole strip of new tiles laid against a pad joins it (`TryGetAdjacentOwner` + a fixed-point loop) → (c) only a tile touching NO existing lane tile falls back to nearest-facing door (`ChooseDoorForNewTile`). This is what makes extending a dock's lane block grow the existing pad instead of getting grabbed by a closer door (the door-5 tiles picked up by door 7 bug). Then persisted/locked.
   - **To re-home mis-owned lanes** (e.g. a door was placed too close before the lock existed, or you want to move a lane to a different door): delete the owning door (its lanes orphan → reassign to the nearest remaining door they face → re-lock), then re-place the door; or delete & re-place the lane tiles themselves. There's no rename UI yet.
3. Per door, the **wall axis (which lanes sit side-by-side along) comes from THAT door's `transform.forward`**, not from global door spread: `wallIsZ = |fwd.x| >= |fwd.z|`. Lanes RUN in the facing/depth direction; they're separated along the perpendicular wall axis. Group the door's tiles by `round(wallCoord / cellSize)` = one lane.
4. Letter lanes along the wall, **A = the LOWEST wall-coordinate lane** (const `LetterFromHighWallCoord = false` → ascending; flip only for a weird dock). `IndexToLetters` is Excel-style (A…Z, AA…).
5. Write `door.DoorNumber + letter` into every tile's `LaneNo` label (all tiles in a lane show the same name).

**Do NOT** reintroduce a global `DoorsSpreadAlongZ`-style wall-axis pick — that was the 2026-07-03 bug (adding a door on a far/opposite wall in X flipped the axis and lettered lanes as columns).

## Verified geometry (reference)
- 4-door wall: doors grid x=67, y=38/45/53/61, rot=3 (face −X). Lane block x57-63 (depth) × y36-62; per-door clusters (Y gaps between) → 5,6,6,5 lanes = `1A-1E, 2A-2F, 3A-3F, 4A-4E`.
- 5th door: x=36, y=38, rot=1 (faces +X). Pad x40-44 (depth) × y36-39 → 4 lanes `5A-5D`, A at lowest Y.

## Gotchas / workflow
- **The Unity MCP bridge drops on every recompile** (and can't refresh/compile while the Editor is in **Play mode** — stop Play first). Verify compiles by reading `%LOCALAPPDATA%/Unity/Editor/Editor.log` for `error CS`. Use `FindAnyObjectByType` (not the obsolete `FindFirstObjectByType`).
- Lane names update live; to see them, be in Play mode with doors + `Flr-ShipLane` tiles placed (they don't exist in the edit-mode scene — they're runtime/save-driven; `PlacedObjectsContainer` is empty at edit time).
- Only the two entry tiles per lane show a label now (`1A-1` / `1A-7`); interior labels are disabled. See the slot-addressing section.
- **Deleting lane tiles = revert to default, not destroy** (`DeleteState`): a lane tile (`Flr-ShipLane`, `isFloor`) on a foundation is not deleted outright — delete swaps that cell back to the foundation's `defaultFloorTile` and keeps the foundation (`TryRevertCustomTile` → `TryBuildRevertCommand`, undoable, refunds the difference). **Drag-delete:** if the drag captures ANY non-default floor tile, EVERY foundation under the swipe is spared (custom tiles revert, no slab deleted) — same policy as the rack-drag exception (`DragCapturesCustomFloor` + `spareFoundations`); a foundation only deletes in a drag with no custom tiles and no racks. **Requires the ground's `defaultFloorTile` to be set:** `grd_Foundation` → `FloorTile` ✅, but **`grd_YardPadA/B` have a BROKEN `defaultFloorTile` (fileID with no guid → null)** — a custom floor on a yard pad can't revert (it's protected from deletion instead, `CellFloorKind.CustomNoDefault`). Fix by assigning those pads a real default (probably `flr-YardTile`) if yard-pad tile editing is ever needed. To re-home a mis-owned lane you must delete & re-place the tile (delete reverts it to default floor; re-placing makes it unowned → adjacency joins the correct pad).

## Slot addressing + inventory putaway (added 2026-07-03)
Beyond naming a lane `1A`, each lane tile is a numbered **slot** so pallets have an exact spot.
- **`LaneNamingService.LaneSlot`** (`{DoorNumber, Lane, Slot, Cell}`, `Name` → `"1A-03"`). Slot index is assigned in the same Recompute, per lane, by **depth from the door** — **slot 1 = nearest the door = truck load order (FIFO)**. Published as a static `cell → LaneSlot` map (`_slotByCell`, rebuilt every Recompute). Query API: `TryGetSlot(cell)`, `AddressAt(cell)`, `GetLane(door, letter)` (slots ordered 1..N). Geometry is the source of truth — no slot state is stored on tiles.
- **`InventoryService`** is the occupancy layer on top (pallets are keyed by grid cell already). `PutawayToLane(palletId, door, lane)` → next open slot (door-outward, stacking to max height) → `MovePallet` → returns full address. `GetPalletAddress(palletId)` → **`"1A-03-2"`** (spatial slot from geometry + **stack tier** from this layer, tier 1 = bottom, in putaway order). Also `GetPalletTier`, `GetPalletsInLane`, stacking-aware `TryGetNextFreeSlot`.
- **`LaneConfig` / `LaneConfigRegistry`** (`Gameplay/LaneConfig.cs`): per-lane `Usage` (Inbound/Outbound/Both), `Order` (FIFO/LIFO), `MaxStackHeight`. Defaults (`Both/FIFO/MaxStackHeight=2`) until set. Putaway honors `MaxStackHeight`. Keyed `"<door><letter>"`. **Persisted (2026-07-03):** `LaneConfigRegistry.Export/Import` ↔ `SaveData.laneConfigs` (`List<LaneConfigEntry>`), wired in `PlacementSystem.BuildSaveData`/`ApplySaveData`.
- **Usage + FIFO/LIFO are consumed by pick/putaway (2026-07-03):** `InventoryService.LaneAcceptsPutaway` (Receiving/Both) gates `PutawayToLane` — a Shipping-only lane rejects putaway. `LaneAllowsPicking` (Shipping/Both) gates picking. `TryGetNextPick` / `PickNextFromLane` choose the pallet by the lane's order: putaway order across the lane is slot 1→N then tier bottom→top (`LaneContentsInPutawayOrder`), so **FIFO** takes element 0 (first placed) and **LIFO** the last (most recent). `LaneSetupUI`'s occupancy line shows the "Next out (FIFO/LIFO)" pallet. Physical accessibility (a FIFO pallet buried behind others in a single-entry lane) is NOT modeled yet — order selection only. Nothing calls `PickNextFromLane` in normal play yet (no truck-loading loop).
- **Lane setup UI (2026-07-03):** `LaneSetupUI` (`Gameplay/LaneSetupUI.cs`) — self-bootstrapping, **code-built** UI-Toolkit modal (no UXML, dodges the RackSetupUI parse pitfalls; finds a `PanelSettings` from any scene `UIDocument` like `ChevronTooltipUI`; shown/hidden via `display`, never SetActive). Edits one lane's `LaneConfig` (Max Stack Size / Usage=Receiving·Shipping·Both / FIFO·LIFO) and writes it via `LaneConfigRegistry.Set` on Save. Usage labels are player-facing wording: **Receiving→Inbound, Shipping→Outbound**. Opened by `LaneInteractionService` (`Gameplay/LaneInteractionService.cs`), an always-on service that detects a **double-click** on a lane: lane tiles have no per-tile collider (parent-collider perf opt), so it raycasts the ground → `PlacementGrid.WorldToCell` → `LaneNamingService.TryGetSlot` → opens the modal for that lane. Gated to FSM `IdleState` and skipped while the modal is open. **Themed** to the house style (`ShiftManagerPanel` tokens): navy panel, caramel border, **Lilita One** font (bold title / regular body), orange title, light-blue labels, blue(Cancel)+orange(Save) buttons; header has the **`StagingLaneIdeas.png`** icon (from `_Project/Sprites`) upper-left with the title left-aligned beside it. The icon loads by asset path in-editor; **for a build it must be under a `Resources/` folder** (like `RackBlueprint.png`) or it won't show.
- **Number-key hotkey suppression — `UIModalGuard` (`UI_UX/UIModalGuard.cs`):** the number-row panel hotkeys (1–5) previously fired while typing in a setup modal, opening panels AND stealing field focus (why Max Stack "wouldn't take numbers"). `LaneSetupUI` and `RackSetupUI` `Push`/`Pop` this ref-counted guard on open/close; all five digit handlers (`ToolsWindowController`/`HiringBoardUI`/`EmployeeRosterUI`/`EmployeeListPanelController`/`TopBarUI`) early-out while `UIModalGuard.IsCapturing`.
- **Lane labels only at the two ENTRY tiles (2026-07-03):** interior tiles' `LaneNo` labels are `enabled = false`; only slot 1 (Lane In, nearest door) and slot N (Lane Out, far end) show text, formatted **`<lane>-<slot>`** (e.g. `1A-1` and `1A-7`). Verified in-game: 32 lanes → 64 visible labels of 211 tiles.
- **Physical↔data link — `PalletInventoryTracker` (2026-07-03):** self-bootstrapping service that keeps a `PalletData` record in sync with every placed **Inventory-category** object (pallet identity = `PlacedObject.data.category == "Inventory"` — covers Chep/LoadedPlt/cases). Creates a record (`InventoryService.RegisterPhysicalPallet`) when a pallet appears, updates its cell on move, `DestroyPallet`s it when removed; runs off place/delete events + 1s heartbeat (heartbeat catches save-loads). Link is a runtime `PlacedObject→id` map — pallet ids regenerate on reload (nothing external references them yet). So a pallet placed on a lane tile now gets a real address automatically; stacking tier = index in the cell's `_palletsByLocation` list. `LaneSetupUI` shows live lane occupancy (addresses of pallets in the lane) via `GetPalletsInLane`.
- **`PutawayToLane`** still exists as the data-level assign-to-next-slot call; physical pallets are located by where their GameObject sits (the tracker), so a receiving flow that *moves* pallet GameObjects into slots is the remaining piece — `PutawayToLane` moves only the data.
