### Graphics (Ultra) — what actually drives the look
- **Tad hand-tuned the ambient occlusion in `Assets/Settings/PC_Renderer.asset`** (SSAO: `Intensity 0.6`, `DirectLightingStrength 0`, `Radius 0.3`, `Falloff 100`). That is the setting he is happy with — don't "improve" it. SSAO only darkens the AMBIENT term, so it reads as grime ("coal miner") on characters whenever ambient gets stronger (exposure up, `DayNightCycle.globalBrightness` up). Re-check it if lighting is raised again. `Good_Renderer` SSAO now matches Ultra's tuned look (`Intensity 0.6`, `DirectLightingStrength 0`, `Radius 0.3`, `Falloff 100`) but keeps its cheaper `Downsample`/`Samples`/`BlurQuality`.
- **The main camera ignores every scene Volume** (`m_VolumeLayerMask: 0` on it in `Main.unity`): the whole grade comes from the project's DEFAULT volume profile, `Assets/Settings/SampleSceneProfile.asset` (contrast -10, saturation -20, ACES, **post-exposure +0.4 EV** = ~+25% brightness). `PP_Ultra`/`GlobalPostProcessProfile`/`PhotoBoothPostFX` do not touch the game view. Live edits to the default profile need `VolumeManager.instance.SetGlobalDefaultProfile(profile)` or nothing changes.
- **`PC_RPAsset` Color Grading Mode must stay HDR** (`m_ColorGradingMode: 1`). A bulk settings rewrite flipped it to LDR once and everything blew out neon. The same rewrite also touched four files in one second — check `git diff` on `Assets/Settings` when colours suddenly change.
- `DayNightCycle.globalBrightness` barely moves the final image (ACES compresses it); use post-exposure for brightness.

### Addendum 2026-10-11 — grain/flicker on avatars = Receive Shadows on the avatar material
Grainy, flickering speckle on avatars (worse in motion) was shadow acne from the avatar's own shadows. Fix (Tad, in the Inspector): **Receive Shadows OFF on `__Avatar_System2.0/Textures/AA_atlas-LPAP.mat`**. It was NOT SSAO (Downsample/NormalSamples changes did nothing) and NOT the cavity pass (cavity intensity only changes the polygon-edge lines, which are the game's low-poly look - never tone them down). Side effect: avatars no longer receive cast shadows from racks etc. (foot contact shadow still grounds them). Tad also retuned `Cavity_Material06-07` himself (Exponent 1.5, Intensity 2, Radius 1.5, Sharpness 0) - left uncommitted by me.

### Addendum 2026-10-17 (night) - Pallet LIFECYCLE status, save/load audit, cross-door overflow, HOT head eyes
**Pallet lifecycle (Tad's spec):** `PalletLifecycle { Unknown, Available, InTransit, Reserved, Staged, Loading, Shipped }` + `PalletLifecycleResolver` (`Core/Inventory/PalletLifecycle.cs`). DERIVED on demand from parent / order tag / inventory record / live work queue, never stored (two stores of one fact have bitten this project twice), so it is correct the moment a load finishes. Unknown = offloaded or on an inbound trailer, not received (no LoadId). Available = received, no claim. InTransit = riding anything. Reserved = a live Replenish or PalletPick task names it (`IsReservedByTask`), or it is a pick-face pallet a released order still needs. Putaway does NOT reserve (an order may take a received lane pallet directly). Staged = outbound on the floor of a lane. Loading = OutboundPalletBuilder.Stage Loading. ### Addendum 2026-10-20 — reach trucks: frame-rate-dependent grab test, log-spam stalls, queue starvation, fleet-wide flat batteries
Symptom: "reach trucks move jankily / slide, and 34 putaways are not getting assigned." Four separate causes, all fixed in `ReachTruckOperator.cs` / `EquipmentBattery.cs` / `ReplenishmentService.cs`:
1. **THE grab test depended on frame rate (the real reason putaways never completed).** `InsertToGrab`, `PickupFromReserve` and `DeliverPalletToRack` extend the forks by `speed * Time.deltaTime` and test "anchor within 0.15 m of the pallet" (0.05 m for the rack place) ONCE per frame. The `[InsertToGrab-DIAG]` lines show it: anchor z -23.08 -> -17.88 passing through the pallet at -21.91. 2. **Log spam stalls.** Every claim poll warned "not the exit-most accessible pallet ... Skipping" per task per truck (34 tasks x 2 trucks) with a stack trace each: 0.2-0.5 s hitches in the Editor. 3. **Failing replenishments starved the whole queue.** Three replenishments could never extract their pallet (cause 1), were retried every 60 s and, being older than the putaways, won the FIFO claim every time. `ReleaseTaskWithBackoff` now backs off exponentially (60/120/240/480/900 s); a Replenish that fails 3 times is CANCELLED and `ReplenishmentService.MarkUnextractable` skips that pallet for 30 min so the scanner doesn't instantly re-file it.
